## Milestone 6 — Story (in progress)

### Round 3: the item guard in `issue_refund` (2026-10-06)
**Why:** in `dev-dmg`, Flash-Lite picked the damaged item itself when the customer only said "something from my order arrived broken" (3 of 3 tries), once sending a $329 refund for the wrong item to approval. A wrong guess under $50 would be paid automatically. Julian's decision: fix it in code, not the prompt.

**What it does:** on an order with more than one product, a damaged refund is only accepted for an item the customer named in their own messages. Otherwise `issue_refund` refuses with `ITEM_NOT_NAMED_BY_CUSTOMER` ("Ask them which item from order #… is damaged; don't choose one for them"), listing the order's items and the ones the customer did name. Single-item orders and the other refund reasons (lost, late) are unchanged.

**How "named" is decided** (`server/src/policy/item-mentions.ts`, pure):
- The customer's text contains the item's product id, or a word of its name that no other product in the order has. The word must be at least 3 characters; plurals count either way ("headlamps", "kid").
- So for #1074 (Voyager 80 pack, Squall jacket, Firefly Kids Headlamp), "It's the kids' headlamp, the Firefly" names the Firefly, and "Something arrived broken" names nothing. "Lamp" doesn't name the headlamp (a fragment), and "80" never names the Voyager 80 (too short; it could be a price).
- **Not quite the matcher Julian named, and why:** `findOrderItem` answers the opposite question. It requires every word of the agent's short query to be in the item's name, so a whole customer message never matches. The new function shares its word splitting (`words` moved into the new module, and `common.ts` imports it).
- It checks only the customer's messages (the conversation loop passes them in `ToolContext.customerMessages`), never the agent's arguments, so naming the item in the call doesn't get past it. Outside a conversation (CLI, unit tests) there's no customer text, and the guard doesn't apply.

**The case validator checks the same thing:** every expected damaged refund on a multi-item order must be for an item the case's customer names. All 153 cases pass, so the guard can't block a refund the frozen test set expects. Four test cases have multi-item damaged refunds (`test-refund-within-limit-01`, `test-refund-over-limit-10`, `-11`, and dev `refund-within-limit-03`); each customer names the item.

**Tests** (516 server + 55 web pass):
- the matcher: turn 1 and turn 2 of `refund-within-limit-03`, several messages, product ids, plurals, fragments, numbers, a word shared by two items
- the tool: a guess refused with nothing written; the wrong item refused even when it would only be queued ($329, no approval row); the named item refunded; the agent's own wording doesn't count; one-item orders and lost refunds unaffected
- the conversation loop passes the customer's messages (a two-turn chat: guess refused, named item refunded)
- the validator's new message
- **One existing test changed its script, not its assertions:** `grade.test.ts`'s script-mismatch test scripted an agent that guessed and refunded at once. That's now refused, so the scripted agent instead replies without asking on turn 1 and refunds on turn 2. Every assertion is the same.

**Prompts:** unchanged (round-2). `issue_refund`'s description gains one clause: "on an order with more than one item, only one the customer has named; if they haven't said which, ask".
