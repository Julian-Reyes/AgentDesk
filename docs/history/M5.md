### The public site: a static snapshot on GitHub Pages (built 2026-10-05, not deployed yet)
**Why:** Julian decided against a hosted server (2026-10-05). The public site is a read-only copy of the dashboard and storefront, with no API and no database. All real work, and every admin action, stays on his machine. GitHub Pages is free only for public repos, so he'll make the repo public; the history was checked for secrets first.

**How it works:**
- **Export (`npm run export:static` → `site-data/`):**
  - It calls the real API in-process, against the local dev DB, for every GET the public site makes. One file per eval conversation (all 9 runs, 1,199 files, 23 MB), so pages load only what they show.
  - Output is deterministic: two exports give identical bytes except `meta.json`, which holds the date and commit.
  - It refuses to run with uncommitted changes outside `site-data/`, so the footer's commit is the code that made the data.
  - It's read-only on the database: the example approvals are added inside a transaction that's rolled back, and a test checks nothing changed.
  - File names come from one shared function (`web/src/lib/static-path.ts`). Query parameters are written `key~value`: an earlier `key=value` broke, because browsers send `=` as `%3D` and the preview server didn't map it back.
- **Static mode (`VITE_STATIC=1`, base from `VITE_BASE`):**
  - The web app's one request function reads the snapshot and refuses anything but GET.
  - Hidden: the admin token box, approve/reject, and the Live runs tab.
  - Every page has a "data as of <date>, commit <sha>" footer.
- **Approvals:** the 5 examples from `server/src/seed/demo-approvals.ts`:
  - 3 pending: a $518 lost refund, a $349 damaged bag, and a 15% coupon
  - 1 approved: $457 lost
  - 1 rejected: a 20% coupon

  They're made by the real tools and the real approve/reject code, on customers and orders no eval case uses (a test checks this), and they're never part of `db:seed`. Each is numbered 1–5 and marked `example`, and the page shows a banner and an "Example" badge.
- **Storefront chat recordings:** `GET /api/replays` (`server/config/replays.json`) has 6 passed Flash-Lite test-1 conversations: a comparison, a buy-2-get-1 total, a lost order, a $229 refund sent for approval, an unknown coupon, and another customer's order. Each has the live widget's progress labels. The static storefront plays them, labelled as recordings, with no text box; each links to its full trace. A recording whose conversation didn't pass is dropped, as with the overview's examples.
  - One candidate was swapped: `test-recommendation-01` passed, but its reply offers to "add to a cart", which the agents can't do (a known weakness).
- **Per-run judge (all pages):** each eval run is shown with the judge that judged it. pilot-1 (judged only by Gemma 4 31B, rubric@1) now reads 3 pass / 2 fail, as its report did, instead of 5 "judge pending". It's labelled "older judge setup, not comparable with later runs".
- **CI:**
  - The check job also builds the static site, on every push and PR.
  - On `main`, a `deploy-pages` job publishes it, only after typecheck, tests and the build pass.
  - The export grades each run once (a cache on `RunsDeps`, used only by the export).
